# Real mr-boxington integration QA — 2026-10-25

The base suites passed **98/98 functional scenario runs** across native Cargo
and the real `mbx` backend. An additional **36 embedded-path/input runs passed
34/36**: all checkout-path assertions passed, while two same-root marker edits
returned stale included bytes. A deterministic follow-up reproduced that
Git-stat-cache invalidation failure **3/3 times per backend**, including Rust
1.89.0. It is tracked in [#118](https://github.com/r4ai/buildq/issues/118).

A separate cancellation experiment found another shared-target correctness bug:
`SIGTERM` can release a member while its build script is still running. With the
native Cargo backend, that orphan overwrote a subsequent successful build's
`OUT_DIR`, and the next successful run printed the cancelled build's value.
The orphan-process symptom also reproduced with the real mbx backend; the
wrong-output consequence was reproduced only with native Cargo.
These are executable integration probes, not a claim that every Rust workspace
or cancellation path is covered. Large-OSS throughput comparisons are recorded
in the companion overall QA report.

## Embedded paths, include_str! inputs, and a false-clean Git stat cache

[`paths.py`](../../scripts/qa-2026-10-25/mbx/paths.py) uses two worktrees sharing
one member per backend. Its output includes `env!("CARGO_MANIFEST_DIR")`,
ordinary `file!()`, `file!()` in an absolute-path `include!`, runtime cwd,
`include_str!(concat!(env!("CARGO_MANIFEST_DIR"), "/marker.txt"))`, and an ordinary
relative `include_str!`. Markers are five bytes and have identical backdated
mtime `946684800000000000` ns (2000-01-01 UTC).

The main sequence alternates `ALPHA`/`BRAVO` worktrees, returns to warm roots, then
edits `ALPHA` to `DELTA` in the same root. A second `--same-marker-only` sequence
uses identical `ALPHA` bytes in both roots, isolating checkout-path keys from
included-content differences.

| Rust 1.91.1 | 10/12 passed; both backends returned old `ALPHA` after the same-root `DELTA` edit | 6/6 passed | 3 |

All 36 runs embedded the correct current worktree path, including genuine mbx
cache-hit restores. No stale checkout root was observed. The two failing marker
runs did not invoke a compiler and did not report an mbx cache hit: buildq said

### Confirmed source invalidation bug: tracked edits hidden by Git's stat cache

Tracked in [issue #118](https://github.com/r4ai/buildq/issues/118).

[`backdated.py`](../../scripts/qa-2026-10-25/mbx/backdated.py) removes the
checkout-path variables from the reproduction: one ordinary package, one
tracked `marker.txt`, and `include_str!("../marker.txt")` in its main program.
It first warms `ALPHA`, refreshes a clean `ALPHA` index entry in a new clock
second, then writes equal-sized `DELTA` and restores the same old mtime within
that stat-cache second. These are normal tracked files: index flag `H`, no
assume-unchanged setting, and `core.trustctime`/`core.checkStat` unset (defaults).

With Rust **1.89.0**, native Cargo failed **3/3** repetitions and real mbx failed
**3/3** repetitions: every edited run exited 0 and printed `ALPHA`, although
`marker.txt` contained `DELTA`. This establishes a Git-stat/timing condition;
the first incidental failures on 1.91.1 are not evidence of a compiler-specific
regression.

Each before/edited/after-job snapshot shows:

- Identical inode, five-byte size and backdated mtime; ctime nanoseconds changed,
  but both ctimes fall within the same second.
- `git status --porcelain` returned empty and the index retained the old blob
  `cd5927f442dec624faffe02e33339b878ee56784` (`ALPHA`).
- `git hash-object marker.txt` returned the actual new blob
  `8fdf8f759280b890890bf48af545126e14887aba` (`DELTA`); the Rust source hash stayed
  unchanged.
- The pool's `m0.manifest` continued to record the old `ALPHA` blob, even after
  the successful-but-stale job.

`git::manifest_in` trusts index blob IDs for paths not reported dirty by Git.
Here that stat-cache shortcut prevents the content change from reaching package
invalidation. Advancing the marker's ordinary mtime recovered **all six** cases:
the next run printed `DELTA`, and `m0.manifest` updated to the actual new blob.
This separates the dirty-detection failure from package ownership, an uncovered
path dependency, the staged-run copy, or mbx cache restoration.

Full `git status`, `ls-files -s/--debug/-v`, `hash-object` outputs, file stats,
pool manifests and recovery outputs are retained in
[`backdated-results/results.json`](../../scripts/qa-2026-10-25/mbx/backdated-results/results.json).
The provenance records Git 2.52.0 and Rust 1.89.0; all index mutations happened
inside disposable fixture repositories.

## Free-space pressure during an active build

[`pressure.py`](../../scripts/qa-2026-10-25/mbx/pressure.py) used an executable
9 GiB tmpfs under `/tmp`, with separate native/mbx fixture directories. After a
warm build with monitoring disabled, it set `min_free` to the volume's then-free
bytes minus **24 MiB**. Its build script gradually writes at most 64 MiB and
waits for a sleep child. This crosses the deliberately high reserve while
leaving nearly 9 GiB free; it does not fill the machine's disk.

| Backend | Bytes written before abort | Result | Descendants / queue | Recovery |
| --- | ---: | --- | --- | --- |
| Native Cargo | 26,214,400 (25 MiB) | exit 125 after 1.436 s | Build script and sleep terminated; zero busy holders | Remove fixture pressure file; same `m0` builds successfully |
| Real mbx | 26,214,400 (25 MiB) | exit 125 after 1.345 s | Build script and sleep terminated; zero busy holders | Remove fixture pressure file; same `m0` builds successfully |

The guarded free-space abort correctly stops the descendant tree in both
backends. This distinguishes reserve enforcement from the SIGTERM bug below.
Exact reserve/free-byte counts, PIDs and recovery checks are in
[`pressure-results/results.json`](../../scripts/qa-2026-10-25/mbx/pressure-results/results.json),
with command logs and idle-slot snapshots alongside it. Actual ENOSPC was not
induced.

## Confirmed cancellation bug: a freed member still has a live writer

Tracked in [issue #111](https://github.com/r4ai/buildq/issues/111).

[`lifecycle.py`](../../scripts/qa-2026-10-25/mbx/lifecycle.py) starts an ordinary
Cargo package whose build script waits for its `sleep 45` child. Once both PIDs
are recorded, the probe sends a signal to the **buildq PID**, waits for buildq,
and checks both Linux process state and queue holders. `kill_tree` remains at
its default `true`; `cache.min_free="0"` selects the ordinary execution path.

| Signal to buildq PID | Native Cargo backend | Real mbx backend |
| --- | --- | --- |
| SIGTERM, two independent repetitions | Exit 143; build script and sleep still executing after 8 seconds; zero busy holders, both times | Exit 143; mbx-real build script and sleep still executing after 8 seconds; zero busy holders, both times |
| SIGKILL, two independent repetitions | Both descendants terminated and slot released in 0.134–0.140 s | Both descendants terminated and slot released in 0.055–0.203 s |

An additional run with `min_free="1"` enabled reserve monitoring without
inducing pressure. Both native and mbx backends still exited 143, left the build
script and sleep running after 8.12/8.17 seconds, and reported zero busy holders.
This confirms the same SIGTERM problem through the guarded execution path.
See [`lifecycle-guarded-results/results.json`](../../scripts/qa-2026-10-25/mbx/lifecycle-guarded-results/results.json).
Use `lifecycle.py --min-free 1 --signals SIGTERM --repetitions 1` to repeat it.

Zombie processes are treated as terminated, not as executing. Native SIGTERM
build scripts were reparented to PID 1, with state `S`, while their sleep child
remained alive. The results preserve PID/PPID, state, command and before/after
snapshots. Test-owned live children were explicitly killed after evidence was
recorded. See
[`lifecycle-results/results.json`](../../scripts/qa-2026-10-25/mbx/lifecycle-results/results.json)
and the paired `*-status.json` files.

The implementation forwards SIGTERM only to its immediate child
(`exec::nix::forward`). When that child exits, `ChildGuard::drop` kills the
watchdog and releases the inherited locks without first establishing that the
Cargo/mbx descendant tree has finished. By then surviving descendants may have
been reparented. The SIGKILL control takes the different watchdog path and
successfully kills the tree before releasing capacity.

### Concrete wrong-output reproduction

[`signal-corruption.py`](../../scripts/qa-2026-10-25/mbx/signal-corruption.py)
uses one slot and **one pool member**, so the next job must reuse the same
member. The build script sleeps five seconds, then writes a value into
`OUT_DIR/value.txt`; the executable includes that generated text.

1. Start a build with value `cancelled-old` and wait until its build script starts.
2. Send SIGTERM to buildq. It exits 143, leaving the build script alive.
3. Immediately run the same package with value `live-new`, zero delay and a new
   marker. Native Cargo reused the exact same `m0` and `OUT_DIR`, completed in
   1.492 seconds, and correctly printed `live-new`.
4. The cancelled build script subsequently finished and overwrote that directory's
   `value.txt` with `cancelled-old`.
5. Run again with the unchanged `live-new` environment. The command **exited 0 but
   printed `cancelled-old`**.

This is output corruption across leases, not just a cosmetic process leak. The
native backend's later job was able to lease and modify a member still writable
by the cancelled build. The current real-mbx control reused the same output path
but waited 5.541 seconds before producing `live-new`, explicitly logging
`Blocking waiting for file lock on build directory`; its final run also printed
`live-new`. The surviving Cargo process still held Cargo's own target lock in
this control. The experiment therefore does not establish wrong-output behavior
for mbx, although its process-lifetime/slot-admission failure is confirmed above.

Raw results and all three command logs per backend are in
[`signal-corruption-results/`](../../scripts/qa-2026-10-25/mbx/signal-corruption-results/).
The runtime was not patched by this QA work.

## Reproduction

Install real mbx 1.27.0, put a working Rust toolchain on PATH, set `BUILDQ_BIN`
and `MBX_BIN` to absolute executable paths, and run from the buildq checkout:

```sh
export BUILDQ_BIN=/absolute/path/to/buildq
export MBX_BIN=/absolute/path/to/mbx
python3 scripts/qa-2026-10-25/mbx/functional.py \
  --root /tmp/buildq-mbx-functional --output /tmp/buildq-mbx-functional-results \
  --toolchain 1.89.0
python3 scripts/qa-2026-10-25/mbx/complex.py \
  --root /tmp/buildq-mbx-complex --output /tmp/buildq-mbx-complex-results
python3 scripts/qa-2026-10-25/mbx/nested.py \
  --root /tmp/buildq-mbx-nested --output /tmp/buildq-mbx-nested-results
python3 scripts/qa-2026-10-25/mbx/lifecycle.py \
  --root /tmp/buildq-mbx-lifecycle --output /tmp/buildq-mbx-lifecycle-results
python3 scripts/qa-2026-10-25/mbx/signal-corruption.py \
  --root /tmp/buildq-mbx-corruption --output /tmp/buildq-mbx-corruption-results
python3 scripts/qa-2026-10-25/mbx/pressure.py \
  --root /tmp/buildq-mbx-pressure --output /tmp/buildq-mbx-pressure-results
python3 scripts/qa-2026-10-25/mbx/paths.py \
  --root /tmp/buildq-mbx-paths --out /tmp/buildq-mbx-paths-results
python3 scripts/qa-2026-10-25/mbx/paths.py --same-marker-only \
  --root /tmp/buildq-mbx-identical-paths --out /tmp/buildq-mbx-identical-paths-results
python3 scripts/qa-2026-10-25/mbx/backdated.py \
  --root /tmp/buildq-mbx-backdated --out /tmp/buildq-mbx-backdated-results
```

Use a new, nonexistent `--root` for every invocation. Existing fixture roots and
nonempty evidence directories are rejected before any fixture writes. The shared
`qa_support.py` assigns each launched command its own session and cleans up owned
sessions on timeout, exceptions and ordinary script exit, including the
intentionally orphaned fixture processes. Linux cleanup verifies PID start times
and includes children in separate process groups within the owned session. All six entry scripts were checked to reject an existing root without creating
the requested evidence directory. A timeout smoke probe also verified that a
Python process and its sleep child were stopped together.

`cc` and `ar` are needed for
the complex suite; Linux `/proc` is needed for process-lifecycle assertions.
The scripts create and modify only disposable local Git repositories, do not
push them, and do not create issues or pull requests on fixture/OSS repositories.
Their JSON `passed` field records the observed expected behavior; cancellation
failures intentionally remain in the evidence instead of being hidden.

Long-term mbx collection, actual ENOSPC behavior, other operating systems and
remote execution are outside these fixtures. Existing integration issues
[#102](https://github.com/r4ai/buildq/issues/102),
[#104](https://github.com/r4ai/buildq/issues/104) and
[#105](https://github.com/r4ai/buildq/issues/105) remain useful tracking points
for maintained real-mbx coverage, additional nested-workspace cases and combined
storage accounting; passing these selected scenarios does not close those
broader requests.
