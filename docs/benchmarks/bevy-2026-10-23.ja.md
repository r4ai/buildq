# Bevy を使った buildq の実測・不具合調査

測定日: 2026-10-23。対象: `7eb2280`、Linux x86_64、Rust/Cargo 1.89.0、release ビルドの buildq。

## 条件と再現方法

- CPU: AMD EPYC 9V74。CPU quota: `400000 / 100000` = 4 CPU。`nproc` は 5。メモリ制限: 16 GiB、swap なし。
- Bevy **0.16.1**、`default-features = false`、`bevy_pbr`, `png`, `multi_threaded`。ロックファイルを fixture に保存。
- 210 コンパイル単位を含む実ビルド。`bevy_render`, `bevy_pbr`, `wgpu`, `naga`, `ash`, ECS、画像処理をコンパイルする。
- dev profile、`debug = 0`、各 Cargo は 2 jobs。buildq は 2 slots、最大 2 pool members、poll 50 ms。
- 同一 Git リポジトリに 4 worktrees。通常 Cargo と buildq のキャッシュを分離し、依存取得後は `--offline --locked`。
- プログラムは `MinimalPlugins` で Bevy を起動し、`Mesh3d` と `MeshMaterial3d<StandardMaterial>` を持つ entity を生成して `App::update()` を実行。`version-A:entities=1` / `version-B:entities=1` を照合する。
- これは描画依存を含む**ヘッドレス実行**の検証。GPU 描画、ウィンドウ、音声、実ゲームのフレーム性能、Windows/macOS/SSH は今回の対象外。
- GC による測定への干渉を避けるため、自動 GC は無効にして測定。後段で実データに手動 GC を実行する。

```sh
cargo build --release
# Python の psutil が必要。約 12 GiB 以上の空き容量を推奨。
python3 scripts/stress-bevy.py \
  --root /tmp/buildq-bevy-new \
  --buildq "$PWD/target/release/buildq"
# 別の新規ディレクトリで、Unix の親プロセス強制終了を検証。
python3 scripts/probe-unix-parent-death.py \
  --root /tmp/buildq-parent-death-new \
  --workspace /tmp/buildq-bevy-new/wt3 \
  --buildq "$PWD/target/release/buildq"
```

`--root` は未作成のディレクトリを指定する。スクリプトは既存キャッシュを削除しない。GC 試験では、この測定専用ディレクトリ内の pool 成果物を削除する。

`logs/measurements.jsonl` にコマンド、終了コード、wall time、ピーク RSS、サンプリング CPU 秒、コンパイル行数を保存する。各 stdout/stderr と queue history も保存する。

## 測定の解釈

RSS は 50 ms 間隔で子孫プロセスを列挙し、同時点の RSS を合計した値。共有ページを重複計上するため、物理メモリの専有量や PSS ではない。短命プロセスを見落とすため CPU 秒は参考値。最初の測定群の wall time には最大約 50 ms の完了検知遅延がある。ウォーム比較は完了を待ち受ける測定器でも再測定する。

コールド測定は各条件 1 バッチ。OS のページキャッシュは消去していない。1〜2% 程度の差を buildq による高速化とは解釈しない。単独ジョブのメモリ削減も主張しない。buildq の効果は、主に worktree 間の再利用と同時ジョブ数の制御にある。

空の独立 target を 3 つ使う対照群と、空の pool を最大 2 members まで使う群を比較する。後者で 3 件目が完了済み member を使えることは、検証対象のキャッシュ共有効果である。既に 1 member が温まった群は別に記録し、全てコールドの群と混同しない。

## 結果

通常経路では、重い依存の再利用、ソース差分検出、キューの同時実行制限、失敗からの復旧、動的リンク実行が機能した。ただし、後述する Unix の親プロセス強制終了と GC の予算維持には運用上の問題がある。

| 条件 | 通常 Cargo | buildq | 解釈 |
|---|---:|---:|---|
| 単独コールド build | 116.05 秒 | 114.32 秒 | 両方 210 `Compiling` 行。各 1 回なので速度差は誤差として扱う |
| 単独コールドのピーク RSS | 1.52 GiB | 1.53 GiB | 単独ビルド自体のメモリは減らない |
| 同一 worktree ウォーム build、中央値 n=10 | 0.203 秒 | 0.220 秒 | 全て再コンパイル 0。中央値の差は約 17 ms |
| PATH に cargo shim を設置したウォーム build、中央値 n=10 | — | 0.235 秒 | 実際の shim 経由でも再コンパイル 0 |
| 別 worktree の最初の build | 独立 target ならコールド相当 | 0.204 秒 | 再コンパイル 0。初期測定のため約 50 ms の計測粒度に注意 |
| 3 worktrees、全てコールドから完了まで | 165.14 秒 | 120.80 秒 | 今回は約 26.8% 短縮 |
| 上記 3 件の同時点ピーク RSS | 4.37 GiB | 2.89 GiB | 約 33.8% 減 |
| 上記のコンパイル行数合計 | 630 | 420 | buildq の 3 件目は完了済み member を再利用 |
| 上記 target の割当済みディスク量 | 3.21 GiB | 2.14 GiB | 約 33.3% 減。通常は 3 target、pool は 2 members |

ウォーム測定の min–max は通常 Cargo 0.196–0.233 秒、buildq 0.206–0.339 秒。17 ms は中央値同士の差であり、固定オーバーヘッドや上限ではない。ソースファイルの少ない fixture なので、Bevy 本体リポジトリの数千ファイルを Git manifest 化するコストまでは示していない。

履歴から求めた buildq の最大同時 build 数は **2**。全コールド群では 3 件目が約 **119.82 秒** 待機してから既存 member を使用した。独立 Cargo 3 件の群は各 `-j2` で同時投入し、全て別 target を使用している。キャッシュ再利用を含むこの条件の測定であり、任意のワークロードで 27% 高速化すると一般化しない。

参考として、1 member がウォーム・1 member が新規の 3 件投入は 116.62 秒、2 members がウォームの 3 件投入は約 0.75 秒で完了した。これらは全コールド群とは分けて扱う。

### 正しさの確認

| シナリオ | 実測結果 |
|---|---|
| ソースを `version-A` → `version-B` に変更し、mtime を 2020 年に戻す | 単純共有では再コンパイルせず **古い A** を出力。buildq はアプリだけ再コンパイルし、3.55 秒で **B** を出力 |
| 元の worktree に戻る | アプリを再コンパイルし、3.55 秒で **A** を出力 |
| Rust の構文エラーを投入 | 終了コード **101** を伝播 |
| 構文エラーを修復して再実行 | 3.66 秒で **A** を出力し、正常復旧 |
| アプリが 5 秒間動作中に別 worktree を build | run slot だけが busy、build slots は空きであることを JSON status で確認。後続 build は **0.206 秒**で完了し、その時点でアプリはまだ実行中 |
| PATH の cargo shim から build/run | build 成功・再コンパイル 0、run は **A** を出力 |
| `--features bevy/dynamic_linking` | 実際に `bevy_dylib` をコンパイルし、実行用ディレクトリへのコピー後に **A** を出力。動的リンク実行も成功 |

動的リンク試験は追加依存をネットワーク取得してから実行した。取得前の最初の `--offline` 試行は `bevy_dylib` 未取得で失敗しており、buildq の不具合や性能値には数えていない。生データでは成功試行名が `bevy-dynamic-linking-fixed-lock` となっているが、Cargo.lock の内容自体は変わっていない。

## 再現した問題

追跡 Issue: [#13](https://github.com/r4ai/buildq/issues/13)（Unix の親強制終了）、[#14](https://github.com/r4ai/buildq/issues/14)（GC の予算超過）。

### P1: Unix では buildq だけの強制終了後も Cargo が残り、キューと実ビルドの寿命がずれる

測定専用の **slots=1、max_members=1** のキューで、Bevy の実コンパイル中に親 buildq だけへ `SIGKILL` を送った。

1. 親は `-9` で終了したが、子 Cargo は生存した。
2. OS ロックの解放により、後続 buildq は build slot と同じ pool member を取得した。
3. 後続 Cargo は `Blocking waiting for file lock on build directory` と表示して停止した。status は後続ジョブだけを表示し、元の Cargo は管理外になった。

根拠: [result.json](data/bevy-2026-10-23/parent-death/result.json)、[replacement.log](data/bevy-2026-10-23/parent-death/replacement.log)。試験後は捕捉した試験用子プロセスを終了させた。

原因は [`src/exec.rs`](../../src/exec.rs) の Unix 分岐。`kill_tree` を使わず、SIGTERM/SIGHUP を直接の子へ転送する処理だけを持つ。SIGKILL 時は実行されない。Windows の Job Object に相当する子プロセスの寿命管理はない。これは既存の Unix 実装の制約であり、今回の変更による回帰ではない。

同じ target では Cargo 自身のロックが最終的な排他を保ったため、今回データ破損は観測していない。ただし、キューの管理対象外で CPU・メモリを使うビルドが残る。別 target/別リポジトリの後続処理まで含めた実同時ビルド上限の保証は失われる。

対策候補は、Cargo の実寿命まで slot/member のロックを保持する監督プロセス、または Linux の cgroup 等によるプロセスツリー管理。既存の `killed_holder_releases_its_slot` テストはスロット解放を確認するだけで、子プロセスの終了までは確認していない。

### P2: 最近の実行用コピーは予算超過時も残り、GC 完了後に予算以下にならない

Bevy の通常・動的リンク実行で生成した実データに `buildq gc --budget 1M --json` を実行した。

- GC 前: **3,275,420,369 bytes**。
- 2 members を削除し、**2,986,353,401 bytes** を解放。
- GC 後: **289,066,968 bytes ≒ 275.68 MiB**。指定予算は **1 MiB**。
- 残った `runs/r0` は **busy=false**。CLI の終了コードは 0。

根拠: [gc-real.json](data/bevy-2026-10-23/gc-real.json)、[cache-after-gc.json](data/bevy-2026-10-23/cache-after-gc.json)。`--budget` はその GC 呼び出しだけの上書きなので、後の cache ls に通常設定の 12 GiB が表示されること自体は正常。

[`src/gc.rs`](../../src/gc.rs) の run dir 削除は、未使用期間が 2 日未満なら予算にかかわらずスキップする。その後の予算強制段階は pool members だけを削除する。このため、「GC でキャッシュ全体を予算以内に保つ」という期待に対し、直近の run copies は例外になる。busy な成果物を残すこととは別の、idle な実データでも再現する問題である。

対策候補は、予算超過時に idle run dirs も LRU 削除の対象にすること。残す方針なら、容量上限がソフト制約であることと、GC 後も超過している状態を CLI で明確に表す必要がある。
