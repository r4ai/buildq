# Bevy を使った buildq のパフォーマンス実測

[English](bevy-2026-10-23.md) | 日本語

測定日は 2026-10-23、対象リビジョンは `7eb2280` である。
通常 Cargo と buildq を使い、Bevy の実ビルド・ヘッドレス実行を比較した。

## 測定条件

| 項目 | 条件 |
| :--- | :--- |
| CPU | AMD EPYC 9V74、CPU quota 4、`nproc` は 5 |
| メモリ | 制限 16 GiB、swap なし |
| OS・ツールチェイン | Linux x86_64、Rust/Cargo 1.89.0 |
| buildq | release ビルド、2 slots、最大 2 members、poll 50 ms |
| Cargo | 各 2 jobs、dev profile、`debug = 0` |
| Bevy | 0.16.1、既定機能を無効化<br>`bevy_pbr`・`png`・`multi_threaded` を有効化 |
| ソース | 同一リポジトリの 4 worktrees、fixture の lockfile で依存を固定 |
| キャッシュ | 通常 Cargo と buildq で分離、自動 GC は無効化 |

初回ビルドは 210 `Compiling` 行を出力した。
描画関連の `bevy_render`・`bevy_pbr`・`wgpu`・`naga`・`ash` と、ECS・画像処理をコンパイルした。

実行プログラムの処理は次のとおりである。

- `MinimalPlugins` で Bevy を起動
- `Mesh3d`・`MeshMaterial3d<StandardMaterial>` を持つ entity を生成
- `App::update()` を実行し、バージョン識別子と entity 数を出力

対象は描画依存を含むヘッドレスの build/run である。
GPU 描画、音声、実ゲームのフレーム性能、Windows/macOS、実 SSH ホストは測定していない。

## 再現方法

uv と、約 12 GiB 以上の空き容量が必要である。
Python と依存関係は `scripts/.python-version`・`pyproject.toml`・`uv.lock` で固定する。
`--root` には未作成のディレクトリを指定する。

```sh
cargo build --release
uv run --project scripts --locked python scripts/stress-bevy.py \
  --root /tmp/buildq-bevy-new \
  --buildq "$PWD/target/release/buildq"
```

依存取得を済ませてから、`--offline --locked` で各ビルドを実行する。
既存キャッシュは削除しない。

保存する測定データは次のとおりである。

- `logs/measurements.jsonl`：コマンド、終了コード、実行時間、ピーク RSS
- 同ファイル：サンプリング CPU 秒、`Compiling` 行数
- 各コマンドの stdout/stderr、キュー履歴

## 性能比較

### 全キャッシュが空の 3 件同時ビルド

| 指標 | 通常 Cargo<br>独立 target | buildq<br>共有プール |
| :--- | ---: | ---: |
| 完了までの時間 | 165.14 秒 | 120.80 秒 |
| 同時点のピーク RSS 合計 | 4.37 GiB | 2.89 GiB |
| target ディスク割当量 | 3.21 GiB | 2.14 GiB |
| `Compiling` 行数の合計 | 630 | 420 |

今回の条件では、時間は 26.8%、ピーク RSS は 33.8%、ディスク割当量は約 33.3% 減少した。
通常 Cargo は独立した 3 targets、buildq は最大 2 members を使用した。
buildq の 3 件目は約 119.82 秒待機し、完了済み member を再利用した。
履歴上の最大同時 build 数は 2 であった。

この比較にはキャッシュ共有の効果を含む。
任意のワークロードで同じ改善率になることを示す結果ではない。

### 単独・ウォームビルド

| 条件 | 通常 Cargo | buildq |
| :--- | ---: | ---: |
| 単独コールドビルド | 116.05 秒 | 114.32 秒 |
| 単独コールドのピーク RSS | 1.52 GiB | 1.53 GiB |
| ウォームビルド<br>10 回の中央値 | 0.203 秒 | 0.220 秒 |
| cargo shim 経由<br>ウォーム 10 回の中央値 | — | 0.235 秒 |
| 別 worktree の初回ビルド | 独立 target なら<br>コールド相当 | 0.204 秒 |

単独コールドでは両者とも 210 `Compiling` 行、ウォームと別 worktree の再利用では 0 行であった。
ウォーム測定の範囲は通常 Cargo が 0.196–0.233 秒、buildq が 0.206–0.339 秒である。
中央値の差は約 17 ms だが、固定オーバーヘッドや上限を示す値ではない。

参考値として、3 件同時投入時のキャッシュ状態別結果も保存した。

- 1 member がウォーム、1 member が新規：116.62 秒
- 2 members がウォーム：約 0.75 秒

これらは全コールドの群とは分けて扱う。

## 正しさの確認

| シナリオ | 結果 |
| :--- | :--- |
| ソースを A から B に変更し、mtime を 2020 年に設定 | 単純共有は古い A を出力<br>buildq はアプリを再コンパイルし、3.55 秒で B を出力 |
| 元の worktree に戻る | 3.55 秒で A を出力 |
| Rust の構文エラーを投入 | 終了コード 101 を伝播 |
| 構文エラーを修復 | 3.66 秒で A を出力 |
| アプリを 5 秒間実行中に後続 build を投入 | run slot のみ busy であることを確認<br>アプリ終了前に後続 build が 0.206 秒で完了 |
| PATH の cargo shim から build/run | 再コンパイル 0、A を出力 |
| `bevy/dynamic_linking` を有効化 | `bevy_dylib` をコンパイル<br>実行用コピーから A を出力 |

出力は `version-A:entities=1` または `version-B:entities=1` と照合した。
動的リンクの追加依存は、測定前にネットワーク経由で取得した。
取得前の `bevy_dylib` 未取得による失敗は、性能比較から除外した。
成功試行の記録名は `bevy-dynamic-linking-fixed-lock` だが、Cargo.lock の内容は変わっていない。

## 測定の限界

- RSS は 50 ms 間隔のプロセスツリー合計
  - 共有ページを重複計上するため、物理メモリ専有量や PSS ではない
- CPU 秒はサンプリング値
  - 短命プロセスを見落とすため参考値として扱う
- 初期測定の完了検知には最大約 50 ms の遅延
  - ウォーム比較は別スレッドでサンプリングする測定器で 10 組を追加測定
- コールド測定は各条件 1 バッチ、OS ページキャッシュの消去なし
  - 単独ビルドの 1〜2% 程度の差を高速化の証拠とは扱わない
- fixture 内のソースファイル数は少数
  - Bevy 本体の数千ファイルを Git manifest 化するコストは未測定
