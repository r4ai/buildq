# Six-Worktree Bevy and mr-boxington Benchmarks — 2026-10-25

The real mbx backend substantially reduced sampled compiler CPU and process RSS
in this workload. It also introduced storage outside buildq's retention budget.
Two combined slots and four combined slots had similar cold completion times;
the extra slots did not establish a throughput advantage in these samples.

## Method

- buildq `3a9e793108ddf1c3bebbd4d1af87cacf0b7ff79f`, release binary
- Real mbx 1.27.0; Linux x86_64, 4-CPU quota, 16 GiB memory limit
- Six actual Git worktrees of the included Bevy 0.16.1 PBR/PNG/multithreading fixture
- Two Cargo jobs per invocation; six simultaneous submissions
- buildq polling interval 25 ms; configured slots/member counts are explicit below
- Separate initially empty outputs and mbx stores for each trial/configuration
- Dependencies fetched before timing; `--offline --locked`; dev profile `debug=0`
- `CARGO_INCREMENTAL=1` at invocation; mbx retains its own internal incremental policy
- Both automatic collectors disabled for this comparison; buildq pool budget 16 GiB, min-free 1 GiB
- mbx views/lanes disabled; scheduler CPU setting 4 and memory setting 12 GiB; remote cache disabled

Configurations:

| Mode | Admission | Targets | Compiler cache |
| --- | --- | --- | --- |
| Plain Cargo | Six Cargo commands start together | Six independent targets | Cargo's local targets |
| buildq 2 | Two build slots | At most two pooled members | Cargo's local targets |
| mbx | mbx compiler scheduler | Six independent targets | One isolated mbx store |
| Combined 2 | Two buildq slots plus mbx compiler scheduler | At most two pooled members | Native `backend="mbx"` integration |
| Combined 4 | Four buildq slots plus mbx compiler scheduler | At most four pooled members | Native `backend="mbx"` integration |

Each configuration runs one cold and two unchanged warm batches. Every build
requests Cargo JSON to identify its executable, then executes that exact artifact
and checks `version-A:entities=1`. The second trial reverses configuration order.
There are 30 batches / 180 checked executables. An independent history audit
confirmed build overlap never exceeded the configured two or four slots, and
member identifiers stayed within their limits.

"Cold" means empty build outputs and compiler-action stores. OS page cache was
not flushed. All roots use the same shared Cargo dependency download cache.
The 60 worktree fixtures were separately hash-checked against the committed
Cargo.toml, lockfile and source.

## Rust 1.89.0 Results

Trial 2 had no other compilation workload running. Tiny diagnostic/tooling
activity was not prohibited; this is a bounded local benchmark, not a dedicated
hardware lab or a statistical performance guarantee.

| Configuration | Cold batch wall | Sampled child CPU | Peak summed process RSS | Cold target + mbx allocated files |
| --- | ---: | ---: | ---: | ---: |
| Plain Cargo | 434.762 s | 1,538.50 s | 7.008 GiB | 6.404 GiB |
| buildq 2 | 146.297 s | 432.25 s | 3.025 GiB | 2.135 GiB |
| mbx | 128.775 s | 215.89 s | 2.018 GiB | 2.657 GiB |
| Combined 2 | 128.025 s | 210.37 s | 1.648 GiB | 2.253 GiB |
| Combined 4 | 130.346 s | 219.98 s | 1.848 GiB | 2.455 GiB |

Relative to buildq 2 in this trial, Combined 2 used about 51% less sampled CPU,
45% less peak summed RSS and 12.5% less wall time, while retained allocated file
blocks increased about 5.5%. Combined 2 and mbx alone differed by less than a
second in cold wall time. These few samples do not support ranking that small
difference.

| Configuration | First warm batch | Second warm batch |
| --- | ---: | ---: |
| Plain Cargo | 0.793 s | 0.680 s |
| buildq 2 | 13.016 s | 12.341 s |
| mbx | 0.797 s | 0.820 s |
| Combined 2 | 1.079 s | 1.023 s |
| Combined 4 | 1.105 s | 0.974 s |

Each warm batch still spans six worktrees. buildq's two members repeatedly
switch source roots, invalidating the local package for path correctness.
mbx can restore eligible matching outputs after Cargo schedules those units.
The cold/warm source-root cost is related to
[#113](https://github.com/r4ai/buildq/issues/113). Cargo freshness/`Compiling`
messages are not equivalent to actual compiler-cache misses; use mbx's counters
and sampled work alongside them.

## Both Collectors Enabled Under Tight Budgets

A separate Rust 1.91.1 run submitted two worktrees in two consecutive waves of
staged `buildq cargo run`. buildq used two slots/members, inline GC, a 768 MiB
retention budget and 1 GiB minimum free space. mbx automatic GC ran with a zero
interval, 256 MiB total/action-store logical limits, a 64 MiB incremental limit
and 1 GiB minimum free space. `mbx settings get` confirmed those effective values.

| Wave | Two-job wall | Peak sampled summed RSS | Combined allocated files afterward | Executable checks |
| --- | ---: | ---: | ---: | ---: |
| Initial | 117.547 s | 1.796 GiB | 1.508 GiB | 2/2 correct |
| Repeated | 89.519 s | 2.161 GiB | 1.287 GiB | 2/2 correct |

These timings describe pressure/recovery rather than an isolated configuration
ranking. Detached/reparented collector CPU/RSS may escape the process sampler;
these are not total GC resource costs. No matching live mbx collector remained
during the half-second quiet check after each wave.

Both collectors did work. A second-wave log records mbx evicting 1,683 objects
and 273 action results (848.5 MiB logical). Its final combined logical usage was
265,037,886 bytes, below its 268,435,456-byte limit. Repeated compilation and
large eviction volumes show retention churn; cache hits alone do not establish
good sustained performance under a small fixed budget split (#106).

All four programs returned the expected result, but buildq's final snapshot was
still above its own budget: 1,353,728,000 bytes, one 1,175,707,648-byte **idle**
member plus two run copies, no busy members and no trash. The earlier collectors
had reported busy protection. A small native fixture independently confirmed
that a GC request skipped under collector-lock contention has no deferred
retry. This does not reconstruct the exact Bevy interleaving; it identifies the
retry reliability gap tracked in [#117](https://github.com/r4ai/buildq/issues/117).
It is a soft-retention limitation, not a failure to enforce a hard quota.

After the throughput confirmation finished, a foreground recovery GC reclaimed
all reported buildq usage to zero. It reported 1,353,740,288 bytes freed, while
unique allocated file blocks across the pool **and** mbx store decreased by
1,105,649,664 bytes. The 248,090,624-byte difference illustrates capacity still
held by mbx hardlinks and accounting overhead, as tracked in #105. mbx data
remained available. This is a file-block accounting comparison, not a measurement
of total device free-space change.

## Measurement Boundaries

Wall time spans the submitted build batch and executable checks. CPU and RSS
are sampled recursively at 50 ms. Short-lived work may be missed; sampled CPU
is not exact `wait4` total CPU. Summed RSS counts shared mappings in each process
and excludes filesystem page cache; it is not cgroup peak memory.

Storage sums `st_blocks × 512` once per `(device,inode)` across every relevant
target, pool and the entire mbx cache. It excludes directories, downloads and
source checkouts. On this overlay filesystem, hardlink sharing is counted once;
reflink sharing was unavailable. The metric is allocated file blocks, not a
measurement of total filesystem/device consumption. Warm relinking/replacement
can change allocation even with collectors disabled.

buildq's own inventory remains a separate accounting system and does not include
the mbx store/private state. Combined reporting and collection are tracked in
[#105](https://github.com/r4ai/buildq/issues/105) and
[#106](https://github.com/r4ai/buildq/issues/106). Do not compare all combined
bytes to buildq's pool-only budget and call that a single-budget violation.

## Reproduction and Evidence

```sh
export RUSTUP_TOOLCHAIN=1.89.0
uv sync --project scripts --locked
cargo +1.89.0 build --release --locked --jobs 2
cargo +1.89.0 fetch --locked \
  --manifest-path scripts/qa-2026-10-25/bevy/fixture/Cargo.toml
uv run --project scripts --locked python scripts/qa-2026-10-25/bevy/run.py \
  --root /tmp/buildq-bevy-six-new \
  --fixture scripts/qa-2026-10-25/bevy/fixture \
  --buildq "$PWD/target/release/buildq" --mbx /absolute/path/to/mbx \
  --clients 6 --trials 2
python3 scripts/qa-2026-10-25/bevy/verify.py /tmp/buildq-bevy-six-new
```

Select the pinned toolchain in the caller's environment for the Python runner.
Use a fresh root and enough disk for six independent targets (over 6 GiB of
allocated files), the dependency cache and any concurrent work.
The runner deletes only its own generated outputs after saving each inventory;
`--keep-targets` retains them. Current runners include bounded command timeouts,
owned-process cleanup and checked mbx diagnostic exits. `--resume` validates
the available provenance and skips only complete saved modes.
