# Artifact Sharing QA — 2026-10-25

The dedupe read limit can permanently block all work behind one oversized
artifact. This is reproduced at `3a9e793` and tracked in
[#108](https://github.com/r4ai/buildq/issues/108).
Content discovery, member-lock exclusion and recovery after a killed pass behaved
as expected in the exercised scenarios. Actual reflink savings remain unverified
because neither available filesystem supports the operation.

## Environment

- Linux x86_64 managed container, overlay filesystem at `/workspace`, tmpfs at `/tmp`
- buildq `3a9e793`, compiled with Rust 1.89.0; release profile for final measurements
- Separate `BUILDQ_DIR` and `BUILDQ_CACHE` for every scenario
- Synthetic artifacts and pool metadata; no external repository modified
- Other QA workers shared the machine; timing samples are **not isolated**

The filesystem probe distinguishes an ioctl's return value from its per-file
status. On overlay, `FIDEDUPERANGE` returned successfully at the syscall level but
reported destination status `-22` (`EINVAL`) and zero deduplicated bytes. Opening
the destination read-write did not change this result. Tmpfs returned
`EOPNOTSUPP` (95). buildq reported the unsupported overlay operation and left
files unchanged. These outcomes establish fallback behavior, not working block
sharing on btrfs, XFS, bcachefs or APFS.

## Safety Scenarios

| Scenario | Observed outcome |
| :--- | :--- |
| Four members; three equal artifact paths and one differing path; hard-linked uplifted outputs | Dry run found 9 duplicate copies, 6 differing pairs; hard links counted once |
| Real pass on unsupported overlay | `shared=0`, `unsupported=FIDEDUPERANGE: Invalid argument`; no errors |
| Identity checks before/after dry and real passes | SHA-256, length, inode, permissions, mtime and link count unchanged for all 20 checked paths |
| One member held under an external `flock` | `skipped_busy=1`; other eligible members still compared |
| Existing dedupe pass holds global lock | Competing pass exits 1 with `another deduplication pass is running` |
| SIGKILL of lock-holding dry-run process | Next dry run succeeds; four 128 MiB sparse pairs compared, no residual global lock |
| Member lock held during dedupe and GC dry run | Both dedupe reports skip that member; no comparisons involving it |

The content-preservation result is for the fallback path. It does not certify
successful Linux sharing or macOS clone-and-relink interruption recovery.
The SIGKILL probe kills an active dry run, not an in-progress macOS clone.
Sparse-file `identical_bytes=0` under allocated accounting is expected.

## Read-Limit Starvation

Two idle members hold these byte-identical pairs:

| Relative path | File size | Comparison budget required |
| :--- | ---: | ---: |
| `debug/deps/libaaa-large.rlib` | 600 KiB | 1,200 KiB |
| `debug/deps/libzzz-small.rlib` | 64 KiB | 128 KiB |

With `dedupe_max_read="1M"`, three real passes and three dry passes all report
`compared=0`, `read_bytes=0`, `read_limited=true`. The real pass persists the
same resume pair, `[["p",0],["p",1]]`, each time. The smaller pair fits the
budget, but is never reached. Increasing the override to `--max-read 2M` makes
the dry run discover both pairs without changing any files.

The limit is checked before comparison and stops the complete pass. Resuming at
a member pair cannot move past an oversized first file within that pair.
The issue is independent of reflink support: no sharing syscall is reached.
The reproducer deliberately uses a small limit; it does not claim a measured
multi-gigabyte artifact in a real OSS build.

Reproduce with:

```sh
python3 scripts/qa-2026-10-25/dedupe/starvation.py "$PWD/target/release/buildq"
```

## Index Scaling

Each sample indexes one toolchain scope containing two idle members with matching
artifact paths. Files are sparse, 64 KiB long. `dedupe_max_read="1"` prevents any
content comparison, so the measurements expose metadata/index/plan overhead
before reading an artifact. The process is restarted for each of three samples.
RSS is the Linux per-process `wait4().ru_maxrss` value, not a sampler estimate.

| Indexed files | Index time, three samples | Total wall time, three samples | Peak RSS range |
| ---: | :--- | :--- | ---: |
| 10,000 | 120 / 169 / 144 ms | 0.162 / 0.241 / 0.206 s | 16.70–16.72 MiB |
| 100,000 | 1,565 / 1,608 / 1,318 ms | 2.234 / 2.148 / 1.777 s | 136.68–136.76 MiB |
| 500,000 | 4,101 / 4,513 / 4,364 ms | 5.086 / 5.660 / 5.440 s | 671.75 MiB |

Every sample reports `read_bytes=0` and `read_limited=true`. The read budget
therefore does not bound indexing time or memory. Closed
[#83](https://github.com/r4ai/buildq/issues/83) introduced per-toolchain indexing
in #100. The remaining single-scope allocation boundary is tracked separately
in [#115](https://github.com/r4ai/buildq/issues/115).

Wall times include contention with other QA workers. In particular, the smaller
release runs had more wall-time contention than the earlier debug runs. These
numbers are not a production throughput claim or a debug/release comparison.
The large test trees were deleted after measurement; filesystem work ended by
2026-10-25 04:27:55 UTC.

## Divergent Copies

Tracked as [#110](https://github.com/r4ai/buildq/issues/110).

A separate bounded probe creates one member per synthetic project, all on the
same toolchain, with the same 16 KiB artifact path and length. Each artifact's
last byte differs. This exercises classification of many distinct contents
without large files.

| Pools / artifacts | Comparisons | Reported read bytes | Wall time |
| ---: | ---: | ---: | ---: |
| 8 | 28 | 896 KiB | 0.011 s |
| 32 | 496 | 15.5 MiB | 0.148 s |
| 128 | 8,128 | 254 MiB | 3.145 s |

The planner compares every pair, `n × (n − 1) / 2`. In the 128-pool case only
2 MiB of distinct input files exist. Reported reads include reading the same
artifact repeatedly. These are actual dry-run comparison counts and timings;
they are not measurements of Linux kernel deduplication or proof that a real
OSS workspace produces this particular distribution of contents.

## Unsupported-Filesystem Preview

Tracked as [#112](https://github.com/r4ai/buildq/issues/112).

On this overlay volume the text preview says `identical: 9 files, would share
3.2 MiB`, and JSON has `unsupported:null`. The subsequent real pass reports
`shared: 0 files, 0 B` and `unsupported: FIDEDUPERANGE: Invalid argument`.
The preview does measure duplicate content as documented, but it does not expose
the already-probed lack of sharing support. Its displayed amount is duplicate
content, not achievable reclamation on this volume.

## Reproduction Artifacts

```sh
# Rebuild HEAD before testing; the preinstalled debug binary was older than HEAD.
cargo +1.89.0 build --locked --release --jobs 2
python3 scripts/qa-2026-10-25/dedupe/probe.py \
  --buildq "$PWD/target/release/buildq" \
  --root /workspace/qa-dedupe-runtime --scale 10000
python3 scripts/qa-2026-10-25/dedupe/concurrency.py "$PWD/target/release/buildq"
python3 scripts/qa-2026-10-25/dedupe/divergent.py "$PWD/target/release/buildq"
```

`probe.py` recreates only its named scenario directories under `--root`; use a
new, dedicated directory. Its raw JSON includes per-command CPU time, RSS,
reports and the before/after file identities. Debug-profile baseline logs are
retained separately as `results-10000.json` and `results-100000.json`.
The [concurrency log](../../scripts/qa-2026-10-25/dedupe/concurrency-result.jsonl)
records both the competing-pass result and successful recovery.
