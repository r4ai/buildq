# buildq performance measurements with Bevy

English | [日本語](bevy-2026-10-23.ja.md)

Measured on 2026-10-23 against revision `7eb2280`.
The benchmark compares real Bevy builds and headless runs through plain Cargo and buildq.

## Setup

| Item | Configuration |
| :--- | :--- |
| CPU | AMD EPYC 9V74, 4-CPU quota, `nproc` reports 5 |
| Memory | 16 GiB limit, no swap |
| OS and toolchain | Linux x86_64, Rust/Cargo 1.89.0 |
| buildq | Release binary, 2 slots, at most 2 members, 50 ms polling |
| Cargo | 2 jobs per build, dev profile, `debug = 0` |
| Bevy | 0.16.1, default features disabled<br>`bevy_pbr`, `png`, and `multi_threaded` enabled |
| Sources | 4 worktrees of one repository, dependencies pinned by the fixture lockfile |
| Caches | Separate plain-Cargo and buildq caches, automatic GC disabled |

The first build produced 210 `Compiling` lines.
It compiled `bevy_render`, `bevy_pbr`, `wgpu`, `naga`, `ash`, ECS, and image-processing dependencies.

The test program performs these operations:

- Start Bevy with `MinimalPlugins`
- Spawn an entity with `Mesh3d` and `MeshMaterial3d<StandardMaterial>`
- Call `App::update()` and print a version marker and entity count

This is a headless build/run benchmark with rendering dependencies.
GPU rendering, audio, game frame rates, Windows/macOS, and real SSH hosts were outside its scope.

## Reproduction

Python with `psutil` and approximately 12 GiB of free disk space are required.
Choose a new directory for `--root`.

```sh
cargo build --release
python3 scripts/stress-bevy.py \
  --root /tmp/buildq-bevy-new \
  --buildq "$PWD/target/release/buildq"
```

Dependencies are fetched before timed builds, which use `--offline --locked`.
Existing caches are not deleted.

The harness saves these records:

- `logs/measurements.jsonl`: command, exit code, wall time, peak RSS
- The same file: sampled CPU seconds and `Compiling` line count
- Per-command stdout/stderr and queue history

## Performance

### Three simultaneous builds with initially empty caches

| Metric | Plain Cargo<br>Independent targets | buildq<br>Shared pool |
| :--- | ---: | ---: |
| Time to completion | 165.14 s | 120.80 s |
| Peak simultaneous aggregate RSS | 4.37 GiB | 2.89 GiB |
| Allocated target disk space | 3.21 GiB | 2.14 GiB |
| Total `Compiling` lines | 630 | 420 |

In this configuration, time fell by 26.8%, peak RSS by 33.8%, and allocated disk space by approximately 33.3%.
Plain Cargo used three independent targets; buildq used at most two members.
The third buildq job waited approximately 119.82 s before reusing a completed member.
History recorded a maximum of two simultaneous build jobs.

This comparison includes cache reuse.
It does not establish the same improvement for arbitrary workloads.

### Single and warm builds

| Condition | Plain Cargo | buildq |
| :--- | ---: | ---: |
| Single cold build | 116.05 s | 114.32 s |
| Single cold build peak RSS | 1.52 GiB | 1.53 GiB |
| Warm build<br>Median of 10 runs | 0.203 s | 0.220 s |
| Warm build through cargo shim<br>Median of 10 runs | — | 0.235 s |
| First build in another worktree | Cold-build equivalent<br>with an independent target | 0.204 s |

Both single cold builds produced 210 `Compiling` lines; warm builds and cross-worktree reuse produced none.
Warm measurements ranged from 0.196–0.233 s for plain Cargo and 0.206–0.339 s for buildq.
The approximately 17 ms difference between medians is neither a fixed overhead nor an upper bound.

Additional three-job batches started with these cache states:

- One warm member and one new member: 116.62 s
- Two warm members: approximately 0.75 s

These batches are separate from the initially cold comparison.

## Correctness checks

| Scenario | Result |
| :--- | :--- |
| Change source from A to B and set its mtime to 2020 | Naive sharing prints stale A<br>buildq recompiles the app and prints B in 3.55 s |
| Return to the original worktree | Prints A in 3.55 s |
| Introduce a Rust syntax error | Propagates exit code 101 |
| Repair the syntax error | Prints A in 3.66 s |
| Submit a build while an app runs for 5 s | Only the run slot is busy<br>The next build finishes in 0.206 s before the app exits |
| Build/run through the PATH cargo shim | No recompilation, prints A |
| Enable `bevy/dynamic_linking` | Compiles `bevy_dylib`<br>The copied executable prints A |

Output was checked against `version-A:entities=1` or `version-B:entities=1`.
Additional dynamic-linking dependencies were downloaded before the successful measurement.
An earlier failure caused by an uncached `bevy_dylib` was excluded from performance comparisons.
The successful record is named `bevy-dynamic-linking-fixed-lock`, although Cargo.lock content did not change.

## Measurement limits

- RSS is sampled aggregate process-tree RSS at 50 ms intervals
  - Shared pages are counted more than once; this is neither exclusive physical memory nor PSS
- CPU seconds are sampled estimates
  - Short-lived processes can be missed
- Initial measurements can include up to approximately 50 ms of completion-detection delay
  - Ten additional warm pairs used a sampler thread separate from the blocking process wait
- Cold measurements use one batch per condition without clearing the OS page cache
  - A 1–2% single-build difference is not evidence of a speedup
- The fixture has few source files
  - Git-manifest costs for thousands of files in the Bevy repository were not measured
